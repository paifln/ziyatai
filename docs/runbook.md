# Эксплуатация ZiyatAI

## Доступность и очередь

Проверяйте /api/health и /api/health/ready. Readiness требует БД, S3 и heartbeat worker менее 60 секунд. Логи содержат jobId/requestId, stage, duration и безопасный code. Не включайте логирование исходных файлов, prompts, email, токенов и query strings auth.

При недоступности worker перезапустите его контейнер. Не меняйте status вручную без проверки lease. Janitor каждые 30 секунд возвращает истёкшие leases в очередь; max 3 попытки, затем failed. Fencing token блокирует публикацию старым worker. Внешний OpenAI может быть оплачен при неопределённом сетевом исходе; AI_UNCERTAIN удерживает консервативный token budget и не повторяется автоматически.

429/5xx используют exponential backoff с jitter. Отказ модели, неправильный формат, ACL и схема не повторяются бесконечно. Cancellation не гарантирует остановку уже отправленного внешнего запроса, но запрещает публикацию отменённого результата.

## Лимиты и хранение

По умолчанию: 25MiB на upload, 150 PDF страниц, 20 листов, 100k непустых ячеек, 2000 строк, 100 uploads и 500MiB исходников на учителя; 100 exports за сутки. Генерации — 20/day user и 200/day service, максимум 2 зарезервированных AI jobs. Token budgets — 200k/day user и 2M/day service, с консервативным резервированием трёх попыток. Изменяйте значения после измерений стоимости и нагрузки.

Временные каталоги удаляются finally, аварийные остатки — через 24 часа. Неимпортированные uploads старше 24 часов удаляет janitor. Материалы сохраняются до удаления учителем. Удаление КТП каскадно удаляет связанные задания и документы; независимое сохранение после удаления исходника в текущей политике не предусмотрено. Account deletion немедленно отзывает сессии, затем worker удаляет S3 и DB snapshots. Backup retention — 30 дней; это отдельные неактивные копии.

## Резервирование и восстановление

Запускайте scripts/backup.sh ежедневно от выделенного технического пользователя. BACKUP_DIRECTORY должен находиться на зашифрованном защищённом томе. Настройте отдельный backup private S3 и проверку целостности export hashes. Целевые RPO 24 часа/RTO 4 часа — эксплуатационные цели, не гарантированный SLA.

Локальная проверка: `npx tsx --env-file=.env.local scripts/restore-check.ts`. Она создаёт pg_dump custom format, восстанавливает в отдельную случайную БД, сверяет число версий и удаляет только созданную временную БД. [Отчёт](reports/restore.json) не доказывает работоспособность production backup.

Для аварийного восстановления остановите web/worker, сохраните текущее состояние отдельно, восстановите backup в новую БД, сверьте миграции и ссылки на S3, выполните private download/E2E и переключите DATABASE_URL только после проверки. Не затирайте единственный исходный volume непроверенным архивом.

## Ротация и инциденты

При подозрении на OpenAI key compromise отзовите ключ у провайдера, установите новый server-side secret, пересоздайте worker и проверьте usage. Для S3 выдайте новый least-privilege ключ, перезапустите web/worker, проверьте Get/Put/Delete, затем отзовите старый. AUTH_SECRET rotation может прекратить существующие сессии: после изменения отзовите сессии и проверьте повторный вход. RENDERER_TOKEN меняется одновременно в renderer и клиентах на отдельном deployment.

Для повреждённых документов сохраните безопасный requestId и renderer version; не прикладывайте приватные файлы в общий тикет. Проверьте fonts, свободный tmpfs, размеры и лимиты. Для сбоя OCR проверьте kaz/rus language data. Для malware check проверьте ClamAV health/signature date; при недоступности система должна отказывать в загрузке.

Monitoring alerts на production ещё не подключены. Нужно настроить хотя бы uptime/ready, queue age >5 минут, рост failed jobs, storage capacity, signature freshness и token budget >80%. Проверьте доставку каждого алерта до публичной приёмки.
