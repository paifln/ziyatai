# Эксплуатация

## Ограниченная роль и проверяемый релиз

API и worker должны получать `DATABASE_URL` ограниченной роли, без CREATEROLE,
CREATEDB, BYPASSRLS и доступа к `auth.users`. Railway использует Shared Variable
`RUNTIME_DATABASE_URL`; административный URL остаётся только в закрытом окружении
обслуживания. Preflight отклоняет привилегированное production-подключение.
Автоматический pre-deploy мигратор API отключён: миграции запускаются отдельно
административным подключением перед обновлением контейнеров.

После миграции выполните `scripts/supabase/provision-runtime.ts ADMIN_ENV NEW_RUNTIME_ENV --apply`.
Команда создаёт отдельную роль, не изменяет пароль существующей роли и сохраняет
новые credentials в закрытый файл. Перенесите только новый `DATABASE_URL` в
`RUNTIME_DATABASE_URL`, привяжите к API/worker и проверьте публичную readiness.
Повторное создание существующей роли намеренно требует отдельной проверки.

Общая квота исходников, экспортов и истории — 1 ГиБ на аккаунт; история одного
материала — до 200 версий. Tombstone занимает квоту до физической очистки.
Экспорты резервируют 32 МиБ и после публикации учитывают фактический размер.
Старые неизвестные размеры учитываются консервативно; их можно уточнить по
проверенному backup-манифесту. История автоматически не удаляется.

## Зашифрованные копии и репетиция восстановления

В отдельном приватном env-файле задайте `BACKUP_ENCRYPTION_KEY` — 32 случайных
байта в hex. Храните его отдельно от backup, включая независимую защищённую
копию ключа. Ключ не передаётся API/worker и не попадает в Git.

`npx tsx scripts/ops/backup.ts PRIVATE_ENV NEW_BACKUP_DIR --online` создаёт
согласованный read-only снимок прикладной схемы и AES-256-GCM архивы S3-объектов.
При активных заданиях команда отказывает; `--maintenance` используется после
остановки записей. Online-режим проверяет наличие используемых файлов и фиксирует
несоответствия прежних checksum как предупреждения, не исправляя данные молча.
Отклонённые загрузки не считаются обязательными рабочими файлами.

Используйте только архив с маркером `COMPLETE`. Проверка:
`npx tsx scripts/ops/rehearse-restore.ts PRIVATE_ENV BACKUP_DIR`.
Она восстанавливает строки во временную схему в одной транзакции, сверяет
количество и fingerprints строк, аутентифицирует и проверяет байты объектов,
после чего откатывает временную схему. Это не заменяет проверку запуска приложения
в отдельном проекте после аварии и не восстанавливает Supabase Auth.

Расписание, независимое место хранения, срок backup и восстановление самого
Supabase Auth согласуются отдельно. Локальная копия не является off-site backup.
Незавершённый каталог без `COMPLETE` нельзя считать точкой восстановления.

## Наблюдение и нагрузка

`node scripts/ops/health-monitor.mjs` проверяет внешнюю readiness с ограничением
времени и ненулевым кодом выхода при сбое. Подключите его к внешнему мониторингу
с уведомлениями владельцу. Readiness включает БД, Storage, worker, renderer и AV.
Логи `api_request` содержат route-шаблон, статус, request ID и время обработчика;
параметры URL, cookie и тексты документов в эти события не включаются.

Для staging: `k6 run scripts/checks/staging-load.js` с `STAGING_ORIGIN` и cookie
синтетического пользователя в `SESSION_COOKIE`. Сценарий не создаёт аккаунты,
не пишет файлы и не вызывает AI; production-домены отклоняются.
Ожидаемую нагрузку и запас масштабирования задают перед приёмкой.

## Проверка готовности

`node scripts/deploy/laptop-backend.mjs status` проверяет контейнеры и публичный `/api/health/ready`. Liveness подтверждает работу API; readiness — доступ к БД, Storage и свежий heartbeat worker. Это не проверка доставки почты, качества AI или всей цепочки экспорта.

При 503 проверьте Docker Desktop, интернет и состояние контейнеров. Затем доступность Supabase, приватного bucket, renderer и ClamAV. Не выводите заполненные env-файлы или полные ошибки провайдера в публичные логи.

## Обновление

1. Выполните проверки из README и дождитесь зелёного CI текущего коммита.
2. Перед изменением схемы сделайте резервную копию; дождитесь завершения записывающих задач и остановите web/worker.
3. Примените новые миграции одним runner: `npm run migrate` с окружением целевой БД. Применённые миграции не редактируйте.
4. Пересоберите образы web/worker/renderer и запустите backend по [инструкции](laptop-hosting.md).
5. При изменении frontend опубликуйте чистый Git-коммит командой `node scripts/deploy/laptop-backend.mjs publish`.
6. Проверьте регистрацию, импорт и экспорт синтетического материала. `workflow-smoke.ts --fixture-export` не вызывает AI; настоящий AI-проверочный запрос требует отдельного запуска.

Остановка через `Stop online.cmd` проверяет очередь и отказывает при незавершённых задачах. Остановка контейнеров не удаляет Supabase или локальные резервные копии. При откате используйте совместимые образы предыдущего коммита; восстановление старой БД поверх новых записей не является безопасным откатом.

## Резервные копии

База и файлы резервируются отдельно. Уточняйте доступность и срок хранения managed backups в тарифе Supabase. Для независимой копии используйте логический PostgreSQL dump, отдельную копию приватных S3-объектов и защищённое хранение конфигурации. Секреты передавайте через окружение или secret manager, не через командную строку и Git.

Проверяйте восстановление в отдельный проект/БД: состав таблиц, количество строк, контрольные суммы, связность владельцев и наличие файлов. Проверка списка содержимого dump не доказывает восстановимость приложения. Сохраняйте исходник до приёмки назначения. [Скрипты переноса Supabase](supabase.md) выполняют сверку данных и не разрешают перезапись непустого назначения.

Ранее созданные `.local/backups/` и старые локальные Docker volumes сохраняются. Удаление исходников и старых отчётов не означает разрешения удалить эти данные.

## Секреты и фоновые задачи

Серверные ключи Supabase, S3 и AI не передаются Netlify frontend. При ротации меняйте согласованные backend/worker настройки; proxy secret должен совпадать с Netlify, renderer token — с renderer. После смены настроек пересоздайте контейнеры и проверьте готовность. `python scripts/checks/scan-secrets.py` проверяет отслеживаемые исходники без чтения игнорируемых секретов.

Worker обрабатывает очередь и очистку quarantine. При остановленном worker readiness ухудшается, а незавершённые задачи сохраняются в БД. Повторы используют lease и idempotency; внешний AI не имеет гарантии единственного платного обращения при аварии. Антивирус недоступен — загрузки остаются непроверенными и недоступными для импорта/скачивания.
