# Владелец действия в основном кабинете

Cookies могут смениться в другой вкладке раньше, чем завершится новая проверка сеанса. Пересоздание Workspace по подтверждённому ID очищает старый интерфейс после проверки, но само по себе не защищает от нажатия старой формы в этот промежуток. На предыдущей сборке оба реальных запроса старой формы — PATCH профиля и DELETE аккаунта — получили 200 с cookies второго синтетического пользователя при задержанной проверке сессии.

## Контракт

`AccountClientProvider` создаёт стабильный клиент для текущего ID, полученного от Better Auth. Все бизнес-запросы React-кабинета используют `useAccountApi` или `useAccountClient`; клиент захватывает владельца в замыкании, а не читает изменяемую глобальную переменную при отправке. Это относится к спискам, редакторам, резервным черновикам, jobs, профилю, импорту, генерации и экспорту. Multipart-загрузка, инициализация прямой загрузки и её завершение используют тот же клиент. PUT по подписанной S3-ссылке сохраняет отдельный контракт хранилища.

Клиент отправляет `X-ZiyatAI-Account`. Backend сначала устанавливает настоящего пользователя из cookies и проверяет обязательное подтверждение почты. Затем сравнивает явное намерение с этим ID до загрузки профиля, лимитов бизнес-операций, обработки тела, создания задач и изменений данных. При несовпадении возвращается 409 `SESSION_CHANGED` с `no-store`. Текст ошибки локализован. Клиент инициирует каноническую проверку сессии; запись автоматически не повторяется. После подтверждения нового ID прежний Workspace размонтируется.

Заголовок не является паролем, токеном или заменой проверки ownership. Знание ID не даёт доступ к чужому аккаунту; без действительной сессии запрос остаётся неавторизованным. Повторные и пустые несовпадающие значения не принимаются. Существующие прямые клиенты без заголовка сохраняют авторизацию по сессии и обычные проверки владельца. Поэтому старый опубликованный frontend без этого заголовка ещё не имеет новой защиты от устаревшего UI.

## Развёртывание и ограничения

Новой миграции нет. Сначала обновляют backend, распознающий заголовок, затем frontend. Старый backend его игнорирует, поэтому новый frontend со старым backend не доказывает защиту. В Netlify/Railway-прокси заголовок должен доходить без изменения; проверка подписи gateway и проверка Origin сохраняются. Этот контракт нужно проверить в облаке после доступности размещения.

Нативные действия Better Auth защищаются отдельным плагином, описанным ниже. Lite всё ещё требует собственного клиента и наблюдения за сменой владельца. Уже завершённые операции на сервере не откатываются. Защита от продолжений размонтированного ProfilePanel сохраняется отдельно: старое завершившееся удаление не должно вызывать sign-out нового пользователя.

## Нативные команды Better Auth

`createAccountClient().auth` фиксирует тот же ID для `changePassword`, `revokeOtherSessions` и `signOut`, сохраняя обработку cookies и событий самого SDK. Канонический `authClient.getSession` остаётся без заголовка намерения: он должен обнаруживать фактического нового владельца, а не требовать прежнего.

Плагин `account-intent` запускается после штатного ограничения частоты SDK и до выполнения endpoint. Отказ с неверным владельцем тоже расходует нативный бюджет: три попытки change-password получают 409, четвёртая — 429 с нативным `X-Retry-After`. Правила входа, пароля и OTP не изменены. Проверка Origin и свежести сеанса остаётся у SDK. Подписанный Netlify gateway и ограничение фактического тела auth-запроса 64 KiB выполняются до входа в SDK.

При наличии заголовка плагин читает настоящий сеанс через серверный API с `disableCookieCache: true` и `disableRefresh: true`. Второй флаг важен: первая реализация проверки возвращала 409, но продлевала стареющий сеанс другого тестового аккаунта. Теперь отклонение не меняет его `updatedAt`/`expiresAt`. Отказ не возвращает Set-Cookie. При недоступности хранилища плагин закрывает действие ответом 503, не разрешая команду.

Без настоящего сеанса запрос с явным владельцем получает 401. Узкое исключение — POST sign-out для очистки уже недействительного сеанса, например после подтверждённого удаления аккаунта. Это не позволяет завершить живой сеанс другого учителя: при наличии настоящего сеанса несовпадение всё равно даёт 409. Если первичное удаление уже завершилось, сбой последующей очистки cookies не превращает его в ошибку удаления; активная старая форма перезагружает страницу для канонической проверки. Для удалённого аккаунта открывается гостевой экран; другой текущий сеанс сохраняется. Размонтированная форма не перезагружает новый кабинет.

Нативный выход из меню обрабатывает отказ SDK, сохраняет форму и позволяет повторить действие явно. Размонтированные настройки/форма пароля не продолжают менять состояние, язык, уведомления или навигацию после await. Доставка Set-Cookie из уже отправленного auth-ответа при одновременном входе в другой аккаунт остаётся отдельным сценарием аудита; проверка перед выполнением команды не является откатом её ответа.

## Проверка

`tests/account-intent.test.ts` проверяет сравнение владельца, независимые клиенты, отсутствие повторной записи при конфликте и заголовки multipart. `tests/e2e/account-intent.spec.ts` проверяет настоящую авторизацию и общий guard для чтений и девяти видов бизнес-записи, неизменность профиля/очереди и работу совпадающего владельца. В `workspace-session.spec.ts` реальные cookies второго учителя устанавливаются при удерживаемом запросе проверки сессии: старая форма не должна изменять ни один профиль или удалять аккаунт; после отпускания запроса открывается новый кабинет.

Дополнительные проверки охватывают три нативные команды, повторяющийся пароль двух тестовых учителей, отдельный живой сеанс второго аккаунта, лимит SDK, readonly-проверку стареющего сеанса, параллельные канонические чтения и правильный выход/удаление при отказе очистки. `tests/auth-account-intent.test.ts` отдельно проверяет отсутствие лишнего чтения для обычного входа/OTP, анонимную очистку и закрытый отказ при ошибке БД.
