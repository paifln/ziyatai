# Архитектура

## Компоненты

`app/` содержит файловые маршруты Next.js, серверные страницы и стили. UI-компоненты находятся в `apps/web/components/`; серверные адаптеры — в `apps/web/lib/`. Клиентские точки входа не импортируют базу, ключи, очередь или renderer; это проверяет `npm run check:client`.

`apps/web/lib/auth/` отвечает за Supabase Auth, HttpOnly cookies, привязку внешней личности к владельцу и отзыв сессий. Вход и регистрация используют email и пароль. Подтверждение письмом не требуется; восстановление отключено по умолчанию. Бизнес-модули получают проверенный ID владельца, а не доверяют email или metadata из браузера.

`packages/contracts/` содержит проверяемые контракты входных данных. `packages/domain/` — предметные правила документов, лимитов и редактирования. `packages/document-renderer/` формирует экспорт. Общие пакеты не зависят от Next.js UI.

`apps/worker/` забирает задания из PostgreSQL. Импорт, генерация, экспорт и физическое удаление выполняются в фоне с lease, heartbeat и повторной проверкой актуальности перед публикацией результата. `apps/renderer/` обрабатывает недоверенные документы отдельно от web и worker; у него нет ключей БД, Storage или AI.

## Данные и запросы

Браузер → Netlify → подписанный proxy → API. API проверяет Origin, сессию, владельца, лимиты и контракт. На Netlify остаются только публичные origins, site ID и серверный секрет подписи proxy. Supabase/S3/OpenAI credentials доступны backend и worker.

Supabase хранит Auth, прикладные таблицы в приватной схеме `ziyatai` и приватный bucket. API работает через PostgreSQL/S3 адаптеры. Браузер не получает прямого доступа к таблицам; загрузка файла использует короткоживущий подписанный PUT только для выделенного ключа.

Загрузка → quarantine → ClamAV и структурная проверка → неизменяемый чистый объект → импорт КТП. Генерация использует snapshot подтверждённой строки. Редактирование создаёт новую версию; одобрение учителя относится к точной версии. Экспорт содержит поля ученика и класса.

SQL-миграции в `migrations/` применяются последовательно с контрольными суммами. Применённые файлы, включая историю старой схемы, не переписываются и не удаляются: это необходимо для повторяемой установки и проверки существующей БД.

## Инструменты и размещение

`scripts/` разделён на `dev`, `build`, `runtime`, `deploy`, `checks`, `supabase` и общую `lib`. Основные команды остаются в корневом `package.json`. Секреты, временные отчёты и резервные копии находятся в игнорируемом `.local/` или `.env.local`.

Текущий backend работает на ноутбуке через `infra/compose.laptop.yml`; локальная разработка использует `infra/compose.tools-local.yml`. Будущий Railway изолирован в `.railway/` со своим lockfile. Шаблон не создаёт ресурсов при проверке и использует ту же Supabase.

Проверки: unit — контракты и ошибки; browser — UI без облачных зависимостей; parser/security — синтетические документы; CI integration — отдельный локальный Supabase и реальные транзакции/сессии. Облачный smoke проверяет интеграцию на синтетических аккаунтах. Настоящие AI-запросы всегда запускаются отдельно.
