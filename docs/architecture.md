# Архитектура

## Компоненты

`app/` содержит файловые маршруты Next.js, серверные страницы и стили. `app/globals.css` задаёт порядок импорта `app/styles/`; тема, landing и review подключаются после него. Изменение порядка меняет каскад.

`apps/web/features/{workspace,plans,generations}/` содержит состояние и отображение крупных пользовательских сценариев. Hooks управляют загрузкой, действиями, отменой запросов и черновиками; секции отображения получают типизированное состояние. `apps/web/components/` сохраняет общие компоненты и прежние точки lazy-loading редакторов. `apps/web/lib/` содержит браузерный транспорт, hooks и локализацию.

`server/` — общая серверная часть web и worker:

```text
server/
  config/                  # проверка окружения
  auth/                    # Supabase, cookies, identity, отзыв сессий
  http/
    api.ts                 # admission, auth, CSRF, лимиты, error mapping
    context.ts             # общий контекст владельца и транзакций
    routes/                # обработчики ресурсов
  application/             # общие сценарии, drafts, коллекции
  infrastructure/
    database/              # PostgreSQL
    storage/               # S3, квоты, cleanup
    queue/                 # задания, idempotency, usage reservations
    documents/             # renderer и ограничение чтения файлов
    antivirus/             # ClamAV и политика сканирования
```

Клиентские точки входа не импортируют `server/`, worker, renderer, Node API и серверные SDK; это проверяет `npm run check:client`, включая динамические импорты и re-exports. Отдельный тест собирает граф worker и запрещает зависимость от `apps/web/`.

`server/auth/` отвечает за Supabase Auth, HttpOnly cookies, привязку внешней личности к владельцу и отзыв сессий. `apps/web/lib/auth/client.ts` остаётся браузерным адаптером. Вход и регистрация используют email и пароль. Подтверждение письмом не требуется; восстановление отключено по умолчанию. Бизнес-модули получают проверенный ID владельца, а не доверяют email или metadata из браузера.

`packages/contracts/` содержит проверяемые контракты входных данных. `packages/domain/` — предметные правила документов, лимитов и редактирования. `packages/document-renderer/` формирует экспорт. Общие пакеты не зависят от Next.js UI.

`apps/worker/index.ts` забирает задания из PostgreSQL и управляет polling, heartbeat и janitor. `apps/worker/jobs/` содержит импорт, генерацию, экспорт, удаление и обработку ошибки. Они используют lease и повторную проверку актуальности перед публикацией результата. `apps/renderer/` обрабатывает недоверенные документы отдельно от web и worker; у него нет ключей БД, Storage или AI.

`apps/lite/parts.json` задаёт порядок ES5-исходников Lite. `npm run build:lite` собирает единую закрытую область видимости в `public/lite/lite.js`; HTML и URL статического клиента сохранены. CI проверяет актуальность сгенерированных файлов до пересборки. Подробности — в [описании Lite](../apps/lite/README.md).

## Данные и запросы

Браузер → Netlify → подписанный proxy → API. API проверяет Origin, сессию, владельца, лимиты и контракт. На Netlify остаются только публичные origins, site ID и серверный секрет подписи proxy. Supabase/S3/OpenAI credentials доступны backend и worker.

Supabase хранит Auth, прикладные таблицы в приватной схеме `ziyatai` и приватный bucket. API работает через PostgreSQL/S3 адаптеры. Браузер не получает прямого доступа к таблицам; загрузка файла использует короткоживущий подписанный PUT только для выделенного ключа.

Загрузка → quarantine → ClamAV и структурная проверка → неизменяемый чистый объект → импорт КТП. Генерация использует snapshot подтверждённой строки. Редактирование создаёт новую версию; одобрение учителя относится к точной версии. Экспорт содержит поля ученика и класса.

SQL-миграции в `migrations/` применяются последовательно с контрольными суммами. Применённые файлы, включая историю старой схемы, не переписываются и не удаляются: это необходимо для повторяемой установки и проверки существующей БД.

## Инструменты и размещение

`scripts/` разделён на `dev`, `build`, `runtime`, `deploy`, `checks`, `supabase` и общую `lib`. Основные команды остаются в корневом `package.json`. Секреты, временные отчёты и резервные копии находятся в игнорируемом `.local/` или `.env.local`.

Текущий профиль размещения: Netlify для интерфейса, Railway для API/worker/renderer/ClamAV и Supabase для Auth, БД и файлов; состояние последней приёмки описано в `.railway/README.md`. Резервный backend на ноутбуке использует `infra/compose.laptop.yml`, локальная разработка — `infra/compose.tools-local.yml`. Конфигурация Railway изолирована в `.railway/` со своим lockfile: это отдельный инструментальный проект, а не конфликтующий lockfile корневого приложения. Его проверка не создаёт облачных ресурсов.

Проверки: unit — контракты и ошибки; browser — UI без облачных зависимостей; parser/security — синтетические документы. CI integration настроен на отдельный локальный Supabase, транзакции/сессии, приватный Storage, renderer, ClamAV и worker. `workflow-smoke --fixture-export` проверяет импорт, одобрение и скачивание DOCX/PDF с синтетическими заданиями; OpenAI не вызывается. Для этого нужны работающий Docker и первый успешный CI-прогон. Локальная проверка рефакторинга без Docker не подтверждает этот сценарий.

Ручные и платные проверки описаны в [реестре](manual-checks.md). Облачный smoke выполняется отдельно с явно выбранным окружением.

Netlify offline packaging проверяется в Ubuntu CI. Локальный Windows-прогон

`./webpack-runtime.js`; runtime присутствовал среди virtual modules. Linux-прогон

## Ограничения текущего разделения

SQL и транзакционные границы сохранены при извлечении обработчиков: HTTP routes пока используют PostgreSQL напрямую. Выносить повторяющиеся транзакционные сценарии в `application/` следует при изменении соответствующего поведения, сохраняя один transaction context. Повсеместная repository-обёртка без конкретной задачи увеличит число переходов по коду.

Глобальные CSS-классы сохранены; разбиение на файлы облегчает навигацию, но ещё не изолирует селекторы. CSS Modules подходят для следующего изменения конкретного компонента с проверкой динамических классов. `any` на существующих DB/API boundaries остаётся техническим долгом: его замена требует проверки реальных форматов ответов и ошибок.
